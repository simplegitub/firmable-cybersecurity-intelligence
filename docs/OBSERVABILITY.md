# Observability and Cost Monitoring

## 1. Purpose

This document describes how the Firmable Cybersecurity Sales Intelligence platform can be monitored for data quality, application reliability, evaluation behaviour, and operating costs.

## 2. Current implementation

The current platform uses a Streamlit application to load an organization-level score CSV and provide search, table display, and CSV download functionality.

The evaluation script validates required columns, rejects missing evaluation labels, summarizes scores by human label, and writes CSV and JSON evaluation outputs.

The repository includes a versioned research skill, a versioned analysis prompt, and a documented evaluation framework.

## 3. Evaluation observability

The evaluation workflow provides repeatable evidence about the scoring heuristic.

Useful measurements include:

- Number of labelled evaluation examples
- Distribution of human labels
- Mean, minimum, and maximum score per label
- Missing or invalid input values
- Changes in evaluation results between versions

Evaluation results should be reviewed whenever the scoring logic or input data changes.

## 4. Application monitoring

The following checks should be performed during application testing:

- Confirm that the score CSV loads successfully.
- Record application errors and their timestamps.
- Verify that organization searches return expected results.
- Verify that score fields are present and interpretable.
- Confirm that filtered CSV exports work.
- Review deployment logs when an application error occurs.

Structured logging, request identifiers, latency measurement, and automated error alerts are proposed future improvements; they should not be considered implemented until added and tested.

## 5. Cost monitoring

The current application does not require a paid LLM API to calculate or display the research-prioritization scores. Therefore, no LLM token usage or per-request LLM cost is currently generated by the deployed workflow.

Operating-cost checks should focus on:

- Hosting-plan usage and limits
- Dataset storage and transfer
- Processing time and memory consumption
- Any future paid API or external service usage

If an LLM integration is introduced, record the model, prompt version, request identifier, token usage, estimated request cost, and execution outcome. Never record API keys or secrets.

## 6. Prompt and version tracking

The reusable prompt is stored at `prompts/prospecting_analysis/v1.md`.

When a prompt changes, create a new versioned file and evaluate the change before adopting it. Keep the evaluation dataset and results associated with the scoring or prompt version being tested.

The current deployed application does not execute this prompt as an LLM call.

## 7. Limitations and next steps

1. Add structured application logging.
2. Measure load and search performance.
3. Add automated tests for input validation and evaluation outputs.
4. Track evaluation results across versions.
5. Monitor hosting usage and any future external-service costs.

The purpose of monitoring is to make failures and limitations visible, not to imply that unimplemented monitoring systems are already active.
